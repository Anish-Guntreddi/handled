**Findings**
- Critical: [providers/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/providers/billing.py:32), [providers/__init__.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/providers/__init__.py:122), [config.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/config.py:142), [api/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/api/billing.py:66) leave the unsigned mock webhook as the default billing path. That openness is only safe if the service is truly localhost-only, but the code does not enforce that. If this config reaches any non-local environment, any caller can POST `{org_id, product, external_id}` and [services/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/services/billing.py:66) will upgrade an arbitrary org.
- High: [providers/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/providers/billing.py:87) does verify Stripe signatures, but fulfillment upgrades on any signed `checkout.session.completed` and ignores the session `payment_status`. Stripe’s Checkout Session docs explicitly expose `payment_status` as the fulfillment signal: https://docs.stripe.com/api/checkout/sessions/object. A delayed/unpaid completed session can still promote the org.
- High: [providers/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/providers/billing.py:95), [services/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/services/billing.py:95) only handle the initial checkout-complete event and always mark the subscription/org active. Cancellations, failed renewals, and downgrades are never applied, so premium access becomes sticky after the first checkout. Relevant Stripe lifecycle events live here: https://docs.stripe.com/api/events/types
- Medium: [services/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/services/billing.py:79), [models/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/models/billing.py:37) implement idempotency as `SELECT` then `INSERT` with a unique key fallback. Concurrent duplicate webhook deliveries can race; one request will error at flush/commit instead of returning `fulfilled=false`.
- Medium: [services/audit_dash.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/services/audit_dash.py:154) exports the entire org audit log into memory for CSV/JSON with no cap, window, or streaming. A single `/audit/export` can force a large DB scan and large in-memory response.
- Low: [api/billing.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/api/billing.py:52), [main.py](/Users/anishguntreddi/Documents/hackathon/apps/api/captureos/main.py:75) build the Stripe `success_url` from `request.base_url` and omit the mounted `/api/v1` prefix. On same-host deployments that points at a non-existent route; on split web/API deployments it redirects to the API host, not the billing UI.

I did not find a client-side plan spoof on `build-package`/`export`: those gates read `ctx.organization.plan` server-side. I also did not find a direct cross-org leak on org-scoped `/audit/*` or `/orgs/{org_id}/billing`, and I did not see any response path exposing Stripe keys/webhook secrets.
